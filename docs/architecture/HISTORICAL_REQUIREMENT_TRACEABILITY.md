# Historical Requirement Traceability

Status: **Canonical Phase 0H supporting authority**

Last updated: 2026-07-25

The machine-readable authority is [`config/historical-requirement-traceability.json`](../../config/historical-requirement-traceability.json). Every record has a stable identifier, source, requirement, disposition, canonical destination, rationale, target phase, and evidence.

## Disposition rules

| Disposition | Meaning |
|---|---|
| Preserved | The requirement remains materially unchanged. |
| Modified | The intent remains, but security, privacy, compatibility, accessibility, or lifecycle constraints changed the contract. |
| Replaced | A different current instruction or architecture fully supersedes the inherited requirement. |
| Deferred | The requirement remains possible but has explicit dependencies and a later phase. |
| Rejected | The requirement conflicts with an accepted safety, privacy, or architecture boundary. |

The registry covers the inherited adaptive shell, semantic icons, local-first storage, hybrid search, Gist synthesis, composer intelligence, AI interpolation, backend compatibility, multi-account behavior, offline PWA, push, share target, branding, administrator content, telemetry, source maps, Soapbox installation and development instructions, accessibility, artifact privacy, dependency remediation, and TypeScript migration.

No requirement is considered implemented merely because it is preserved. Current implementation evidence comes from the source-backed inventories and executable gates; accepted targets remain future work until their roadmap exit criteria pass.
